# Agentic AI Board: Design Record

This document records why wave 1 of the vendor-neutral Agentic AI Board ships what it ships, what it deliberately does not ship, and how much of it is evidence rather than intent. It is a dated design record, not an authorization surface: nothing described here approves, executes or deploys anything. Counts are stated "as of 2026-10-30" and are not maintained after that date; the generated count markers elsewhere in the docs are the live source.

## Corrections after independent review

An independent 10-reviewer adversarial review (chair verdict REDESIGN, weighted score 63.2/100, no hard gate failed) found that this record and ADR-0003 contradicted the pull request's own diff and overstated several controls. Most of those defects have since been fixed in code, and this record now describes the code as it is. Each superseded claim is listed here with what is true now.

- **docs/execution-tiers.md was amended in this PR.** This record described it as unchanged and Cursor's behavior as unverified. This PR rewrites the enforcement table in docs/execution-tiers.md: a SKILL.md `allowed-tools` line is marked "No" in Claude Code (it only pre-approves; `disallowed-tools` is the restricting field, per https://code.claude.com/docs/en/skills), and there are rows for the claude-code `tools:` allowlist, the cursor `readonly` field and gemini. Cursor `readonly` is verified as a partial restriction ("restricted write permissions (no file edits, no state-changing shell commands)", per https://cursor.com/docs/subagents). This is a change to a stable-contract document that the owner must explicitly accept or revert.
- **The gemini adapters did not carry "no tool grant".** They omitted `tools`, which per https://geminicli.com/docs/core/subagents/ gives the agent every parent tool: a maximum grant. They now carry a read-only allowlist (`read_file`, `grep_search`, `glob`, `list_directory`; names and Read/Search kinds from https://geminicli.com/docs/reference/tools/), asserted by the suite. The kiro-ide and kiro-cli adapters still carry no verified restricting field and are prompt-level only.
- **The TypeScript per-server MCP-trust entry no longer names the old board.** This record said the entry in the MCP tool-contract companion skill still did. It and its generator source (scripts/typescript_data/agents/11-typescript-mcp-tool-contract-agent.json) now route to agentic-security-review-agent. The TypeScript routing contract (tests/fixtures/typescript-maestro-routing/taxonomy.json) was not changed, so the grader still routes MCP-server-trust tasks to typescript-mcp-tool-contract-agent: prose and routing contract disagree until an inbound route is added (open item RB-19).
- **Inbound routing does not exist.** ADR-0003 said a user or an existing vendor maestro could choose a board agent. No maestro routing taxonomy maps to either board agent, so no maestro routes to the board. It is entered when a user names an agent or when a harness's main agent delegates to it automatically from its description (documented for Gemini CLI). A routing contract still does not exist (RB-19).
- **Rule and fixture counts, and the HARD-gate guarantee.** This record stated 68 rules, 77 invalid fixtures and 10 valid fixtures, and stated the HARD-gate guarantee without saying it held only for attached challenges, which the review showed could be bypassed. There are now 85 rules (HO 34, DR 16, DRC 13, VC 11, STOP 9, CH 2), 12 valid and 108 invalid fixtures, every invalid fixture fails exactly its one declared rule and every rule has a sole-violation fixture. DR-CHALLENGE-COMPLETE closes the bypass; the rules added after the review are listed under "What validate:agentic-board proves". The second independent review superseded these counts: there are now 87 rules, 30 valid and 142 invalid fixtures.
- **Mutation evidence was overstated.** This record cited a probe of 65 sites that killed 64. That probe used deletion operators only, and the independent chair found 5 of 5 targeted comparison, boolean and constant mutants surviving. The suite now commits 15 targeted mutants (TargetedMutantTests) and the corpus kills all 15. A full mutation probe with an enumerated list of equivalent mutants is still open (RB-08, partial). After the second independent review the suite commits 33 targeted mutants, and the corpus kills all 33.
- **The mutation-intent and instruction-bait patterns were mischaracterized.** This record called them broad and fail-closed and said bait negatives were pinned; both claims were wrong. LIVE_GUARD_INTENT and INSTRUCTION_BAIT are low-recall denylist canaries that fail open. The suite now pins known misses, known false stops and bait negatives, and the agents are told to stop on meaning, not on the canary.
- **Other facts now reflected.** The harness adapters are generated by the committed tests/agentic-board-suite/_build_harnesses.py and checked (`--check`) by the suite; they previously came from an uncommitted scratch script and could drift. The install roles cloud-ai-platform-engineer, cloud-security-engineer and typescript-agentic-contract-engineer now install both board agents plus finance-capital-allocation-advisor-agent, which is still unaware of the protocol (RB-15). Budgets are checked per chain only. Pseudonymous subjects are personal data when the organization can re-identify them. A decision-record is never a live-guard approval token.
- **The scorecard gained a row.** Agent behavior is scored 1: no model is run against the agents.
- **ADR-0003 alternative 5 was re-justified.** The two-agent split rested on a rule this PR introduced. It now rests on domain and context grounds, and a seeded-defect comparison that would test it has not been run.

## Corrections after the second independent review

A second independent adversarial review (seven attack lenses: authority bypass, false rejection, semantics, robustness fuzz, mutation adequacy, docs claims, adapters and roles) re-tested the first remediation and reported 51 findings. Every engine finding was reproduced by re-running its probe. Each superseded claim is listed here with what is true now. Where an earlier section conflicts with this one, this one is current.

- **HARD-gate clearance.** The gate accepted three kinds of record that the protocol forbids. A HARD-gate withdrawal attached to the request, although it was sent after the request or after the decision, cleared the gate retroactively. Same-second challenge rounds were ordered by task_id string, so a withdrawal cleared a HARD gate that was re-raised after it. A round-3 withdrawal, honestly stopped as over the round cap, still cleared two sustained HARD rounds. Now DR-CHALLENGE-PRECEDES requires that no attached challenge was sent after the request or descends from it. Order is causal: an envelope precedes another when it is an ancestor of it or was sent in an earlier second. Same-second envelopes with no ancestry are unordered, and no rule treats either as later. Only a completed withdrawal in a strictly later counted round, sent after the finding, clears a HARD gate.
- **Superseding request from another proposer.** A superseding request from a different proposer dropped a HARD gate attached to the request it superseded. DR-ONE-REQUEST now requires the same proposer_agent and also rejects a supersession cycle.
- **R5 dual control on a lower-tier branch.** DRC-SECOND-APPROVER keyed on the decision-record's own tier, so one human approved an R5 request by sending the record on a lower-tier branch. It now also applies when the bound decision-request is R5.
- **Escalated stops.** A stop declared with status "escalated" on a delegate to an agent escaped STOP-TERMINAL. HO-ESCALATE-TO-PRINCIPAL now also covers any envelope with status escalated, because that status means the work is handed to a principal, and no decision-record binds a decision-request that declares any stop reason.
- **Routing-loop revisit.** The "one revisit" routing-loop exemption (STOP-ROUTING-LOOP) allowed six revisits to the same challenger. A revisit is now allowed only while the challenger has answered fewer than 2 of the sender's proposal envelopes in that chain.
- **Returns that skip the delegator.** A reviewer's block verdict sent as a return straight to a principal, skipping the delegating agent, never reached the decision path. The new rule HO-RETURN-TO-SENDER requires a return to be addressed to its parent's sender.
- **False rejections fixed, and three behaviors kept on purpose.** The gate refused legitimate flows that it now accepts: a late challenge cured by superseding the request (a superseded request is judged as of its own sending, and the request in force is still judged up to its decision); a same-second supersede; a principal re-delegating to an agent already in the chain (a routing loop is now agent-sourced only); two findings from one challenger on one proposal envelope (a round is one proposal envelope answered, so several challenges on one envelope share a round); a round-2 revisit delivered after another challenger challenged in between; an R5 decider's record left without a co-signature on a request that was later superseded (a superseded request's record is void and owes no co-signature, and the decision in force still needs its co-signature); and same-second rounds that descend from each other. Three behaviors are kept on purpose and are now documented in the protocol references: a co-signing record must be a child of the decider's record (the decider addresses the record to the second approver); superseding does not cure a request that broke a content rule (restart the correlation); and R5 dual control applies to every outcome, reject included.
- **Crash hardening.** The gate raised a traceback on deeply nested JSON (RecursionError), on unreadable paths and on malformed input to --digest. Every such input now gives HO-SCHEMA or an error message and exit code, never a traceback. Envelopes nested deeper than 32 levels, NaN and Infinity are rejected. --digest prints a digest only for a strict, schema-valid decision-request envelope. An unreadable path exits 2 and later files are still checked. Check time no longer grows with challenges squared per record, because live challenges are computed once per request.
- **Counts.** This supersedes the counts in the first corrections section. There are now 87 rules (HO 35, DR 17, DRC 13, VC 11, STOP 9, CH 2), 30 valid fixtures (12 hand-written valid scenarios plus 18 valid variants that pin a rule's boundary from the accepting side) and 142 invalid fixtures. Every invalid fixture fails exactly its one declared rule, and every rule has a sole-violation fixture. TargetedMutantTests commits 33 targeted mutants and the corpus kills all 33. Fifteen invalid fixtures and several valid variants come from the mutation-adequacy lens's distinguishing probes, each of which kills a mutant that had survived. A full mutation probe with an enumerated list of equivalent mutants is still open (RB-08).
- **Codex `sandbox_mode` was inert.** The board's codex.toml adapters carried `sandbox_mode = "read-only"` as a restriction. OpenAI's subagents page (https://developers.openai.com/codex/subagents, fetched 2026-10-30) says custom agents "inherit the parent's permissions, provider, and MCP servers; a custom agent file can't override those settings" and "Other session settings, including sandbox_mode, approval_policy, model_provider, and mcp_servers, don't override the parent configuration when placed in a custom agent file." So the setting had no effect. The board's Codex adapters now drop sandbox_mode and set `features.shell_tool = false`, the page's documented way to reduce a custom agent's capabilities. No documented per-agent switch removes file editing, so under Codex the read-only limit is the parent session's sandbox plus the prompt. The same applies repo-wide: 735 committed codex.toml adapters carry sandbox_mode, and the model policy projects model_provider into codex.toml. Both keys are inert in a custom agent file per that page. That repo-wide issue is out of this PR's scope and is listed under "Implementation backlog".
- **Gemini is a documented restriction.** This record placed the Gemini allowlist in an "unverified" class while treating the Claude Code `tools` field as verified, which was inconsistent. https://geminicli.com/docs/core/subagents/ documents both that an omitted `tools` field inherits all parent tools and that "the subagent only has access to the tools you explicitly grant it". That is the same documentary basis used for Claude Code, so Gemini's allowlist is classed as a documented restriction (vendor documentation, not a live test), like Claude Code's.
- **Entering the board.** "Only a user can enter the board, by naming an agent" ignored harness automatic delegation. The same Gemini page documents that the main agent may call a subagent when a task matches its description. No maestro routes to the board, so it is entered when a user names an agent or when a harness's main agent delegates to it automatically from its description. A routing contract still does not exist (RB-19).
- **Install-role export coverage, and the gate does not travel.** This record said the install roles carry the board without saying where export stops. cloud-security-engineer and cloud-ai-platform-engineer also contain nvidia-model-promotion-gatekeeper-agent, which has only claude-code and cursor variants, so exporting those two roles to codex, gemini, copilot or kiro aborts (a pre-existing exporter behavior). typescript-agentic-contract-engineer exports on all six platforms. An exported install carries the protocol prose and agents, not the offline gate (tests/agentic-board-suite/agentic_board_rules.py) or the schema; the protocol skill now says so.

### Honesty boundary

- This repository ships role contracts, skills, a JSON Schema and offline gates. It is not an orchestration runtime. Nothing here authenticates senders, enforces authorization at runtime, or stores audit records.
- A valid envelope authorizes nothing. It is a data contract. A record set that passes the gate is well-formed and internally consistent; it is not proof that any approval happened or that any content is true.
- Framework mappings (NIST AI RMF, OWASP, ISO/IEC 42001, EU AI Act) are candidate review aids that an accountable owner confirms. Nothing here claims certification or compliance, and no mapping "satisfies" a framework (see docs/compliance/framework-profiles.md).
- Tool restrictions are declared only where a harness adapter carries a grant. Whether a harness enforces its declaration is a claim about that vendor's product. Vendor documentation, which this record read but did not test live, documents enforcement for the Claude Code subagent `tools` field, the Gemini `tools` allowlist and, as a partial restriction, the Cursor `readonly` field. Codex has no per-agent sandbox: a custom agent file cannot override the parent session's sandbox, so under Codex the read-only limit is the parent session's sandbox plus the prompt. A SKILL.md `allowed-tools` line only pre-approves tools and restricts nothing; `disallowed-tools` is the restricting field. This PR amends the enforcement table in docs/execution-tiers.md, the repository's stable-contract document, to match, and the owner must explicitly accept or revert that change. See "Security, governance and escalation model" for the per-harness table and "Pre-existing defects found" for the amendment.

## Executive verdict

**Wave 1 ships two agents, three skills, one JSON Schema and one offline gate. It ships no maestro and no business-value agent.** The two agents are agentic-system-architecture-review-agent and agentic-security-review-agent, both static-review, with a tool restriction declared in five harness adapters (Codex's is a disabled shell tool, not a read-only sandbox) and a prompt-level limit in the other two (enforcement of each declaration is discussed under the per-harness table). The three skills are the two companion skills plus the shared agentic-board-protocol. The gate is `npm run validate:agentic-board`.

- **Why so small.** The owner asked for the smallest coherent set, not the largest. Three candidate designs were produced and three judges each ranked the "minimal-reuse" design first at 8 out of 10. That is an internal review process, not independent evidence.
- **Why no maestro.** A1 is rejected for this wave. Only two leaves would be owned. Routing is deterministic keyword scoring. Twelve of thirteen proposed targets are already routed by their own provider maestro, so a board maestro would be a divergent second path (the Copilot Studio target conflicts with microsoft-maestro). Refuter probes of tests/validate-maestro-routing.py showed an anchored live-guard pattern routing "destroy the AgentCore runtime in production" to a single agent, aws-agentcore-agent, while the aws taxonomy gates that request. Four proposed targets have no declared execution tier, and three of those hold execute or runInTerminal tools in their Copilot adapters. Re-entry criteria are in ADR-0003.
- **Why no business agents.** E1 to E7 need baseline data that no marketplace repository can reach. The value-case contract in agentic-board-protocol lets a sponsor supply measured evidence outside the repository.
- **What the roster became.** Of 29 candidates: 9 are covered by content inside the two new agents (B1, B2, B3, B5, D3, C1, C2, C4, C5), 1 is split across three owners (B4), 9 are composed from or already exist in the catalog (A2, A4, A5, B6, C3, D1, D4, D5, E8), 1 is deferred (D2) and 9 are rejected (A1, A3, E1 to E7). The table under "Rejected and deferred candidates" is the source for this tally.
- **How far to trust it.** Not Fortune 50-grade: evidence-ready contracts, no production evidence. Every fixture is synthetic, no adopter has run the board, and every runtime guarantee belongs to a product B that does not exist here. The scorecard below shows the evidence level reached per dimension.

## Topology and handoff contract

The envelope in [schemas/agentic-handoff.schema.json](../../schemas/agentic-handoff.schema.json) is the only channel between board agents and principals. The schema checks shape only; the cross-field rules live in tests/agentic-board-suite/agentic_board_rules.py, one predicate per rule id, so each defect fails with the id that names it. There are 87 rule ids in six families as of 2026-10-30: 35 envelope, record-set and chain rules (HO), 9 computed stop conditions (STOP), 2 challenge rules (CH), 17 decision-request rules (DR), 13 decision-record rules (DRC) and 11 value-case rules (VC). The rule tables are in the protocol references: [handoff envelope](../../skills/cross-functional/agentic-board-protocol/references/handoff-envelope.md), [stop conditions](../../skills/cross-functional/agentic-board-protocol/references/stop-conditions.md), [decision record](../../skills/cross-functional/agentic-board-protocol/references/decision-record.md) and [value case](../../skills/cross-functional/agentic-board-protocol/references/value-case.md).

| Message type | Purpose |
|---|---|
| delegate | Ask an agent to perform analysis, phrased as a review question |
| return | Deliver a verdict to the requester |
| challenge | A designated challenger's adversarial finding on a proposal |
| escalate | Stop and hand to an accountable principal, with a route hint |
| decision-request | An agent assembles proposal, alternatives, challenges and dissent for a principal. Never a decision |
| decision-record | The principal's decision, bound to one decision-request by the sha256 of its canonical JSON |

A typical decision, taken from the synthetic fixture for an R3 architecture review with a sustained HARD-gate challenge:

| Hop | Message | From to to | What happens |
|---|---|---|---|
| 0 | delegate | principal to architecture agent | Root of the correlation; parent is null |
| 1 | delegate | architecture agent to security agent | Proposal sent to the designated challenger |
| 2 | challenge | security agent to architecture agent | Round 1, hard_gate true, outcome sustained |
| 3 | decision-request | architecture agent to principal | Recommends redesign; carries alternatives, challenge ids and dissent |
| 4 | decision-record | principal to architecture agent | The principal conditionally approves over the HARD gate with a risk acceptance reference, bound by request digest |

A principal computes request_digest with `python3 tests/agentic-board-suite/agentic_board_rules.py --digest <request-envelope.json>`.

Four properties carry the design, and each is checked by a named rule family rather than asserted by prose.

- **Agents never decide.** Agent-sourced envelopes may carry only not-required or pending-human-review. Only a principal-sourced decision-record carries approved or rejected. A decision-record is a review outcome, never a live-guard approval token or an audit-event approval_id.
- **Monotonic attenuation.** Down a chain, tier, classification, materiality flags and prohibitions never shrink; deadline and max_hops never extend; authorized actions and budget limits only narrow; a missing parent is a violation.
- **Computed stops.** Depth, deadline, budget, blocking missing evidence, mutation intent, instruction bait, routing loops and challenge rounds are computed from message fields, never from the wall clock.
- **No execute verb.** Authorized actions are read, analyze, recommend, challenge and escalate. Live work escalates to a principal with a route hint to the owning provider's gated live-guard path; the hint is never a dispatch.

Principals are opaque individual subjects of the form `subject:corp-idp:<hex digest>` plus a separate role. Self-approval is detected by comparing subjects. A pseudonymous subject is still personal data under GDPR Recital 26 when the organization can re-identify it, so a record set is not free of personal data. The runtime, not this repository, authenticates senders; a subject in a record set proves nothing about who sent it. No field may carry credentials, tokens or secrets, and a committed invalid fixture shows an envelope with an unknown credential-shaped field failing the schema rule.

## Security, governance and escalation model

### Risk tiers

The envelope's subject_risk_tier is the canonical tier of the decision under review. The board's own work is static review. The canonical table, quoted from docs/compliance/applicability-engine.md:

| Tier | Meaning | Gate posture |
|---|---|---|
| R0 | Read-only, non-sensitive | Observe; audit event recommended |
| R1 | Read-only, sensitive data in scope | Read-only-runtime; runtime-evidence-gate; redaction |
| R2 | Reversible non-production change | Plan + policy gate; approval per policy |
| R3 | Production change, bounded, reversible | Independent approval + JIT + rollback + audit event; fail closed if audit unavailable |
| R4 | Production change, broad blast radius | R3 controls + blast-radius assessment + change window |
| R5 | Irreversible / high-blast-radius production action | R4 controls + second approver + explicit risk acceptance |

The owner's proposed scale maps onto it as follows. Owner R0 and R1 map to canonical R0 and R1 by data sensitivity; owner R2 maps to R2; owner R3 maps to R3. Owner R4 (financially material, security-critical, destructive, regulatory or hard-to-reverse) splits across canonical R4 for broad blast radius and R5 for irreversible or high-blast-radius actions, and also sets materiality flags. The flags (financial, regulatory, security-critical, external-communication, personal-data, irreversible) force full-depth review and principal escalation. They never remap the tier. The full crosswalk, the execution-tier crosswalk and the candidate NIST AI RMF mapping are in the [risk-tier crosswalk](../../skills/cross-functional/agentic-board-protocol/references/risk-tier-crosswalk.md). The AI RMF core page carries a banner that version 1.0 is being updated (https://airc.nist.gov/airmf-resources/airmf/5-sec-core/), so treat that mapping as provisional.

### Review depth and the HARD gate

Review depth is proportionate. R0 and R1 without materiality flags need a single specialist and an optional challenge. R2, any materiality flag, or an automation investment needs the designated challenger, at least one materially different alternative, and a dissent entry for every open challenge. R3 and above additionally make a principal decision-record the only way forward, and R5 needs a second approver distinct from the decider. The board never resolves a disagreement by the most confident agent, by voting or by averaging, and dissent is preserved, never deleted.

A security challenge with hard_gate true and outcome sustained or unresolved forbids the proposer from recommending approve or conditional-approve. Only a principal decision-record carrying a risk acceptance reference may approve over it, and agents can never record a gate as overruled.

The override rule holds over every challenge on the proposal, not only the challenges a proposer chose to attach. DR-CHALLENGE-COMPLETE requires every challenge on the proposer's envelopes sent no later than the request (or a decision-record binding it) to be attached, so a HARD gate cannot be dropped by omission or by arriving late. A HARD gate clears only when the same challenger sends a later round that is itself a HARD-gate withdrawal. Before the independent review this record stated the guarantee without saying that it held only for attached challenges, which the review showed was bypassable; DR-CHALLENGE-COMPLETE closes that bypass.

### Candidate threat mapping

The security agent walks all ten items of the OWASP Top 10 for Agentic Applications (2026), ASI01 to ASI10 (names confirmed at https://genai.owasp.org/2025/12/09/owasp-top-10-for-agentic-applications-the-benchmark-for-agentic-security-in-the-age-of-autonomous-ai/). A repository rule is named for an item only where that rule operates on the threat's object; five items have such a rule (ASI01, ASI03, ASI07, ASI08 and ASI09) and the other five (ASI02, ASI04, ASI05, ASI06 and ASI10) are marked runtime-only (product B), because no manufactured coverage is acceptable. ### What validate:agentic-board proves

The gate is deterministic and offline, reading committed files only (`python3 -m unittest discover -s tests/agentic-board-suite -p "test_*.py"`). It proves:

- Every one of the 87 rules has a sole-violation fixture, and each of the 142 invalid fixtures fails exactly its one declared rule.
- The 30 valid record sets (12 hand-written scenarios and 18 variants that pin a rule's boundary from the accepting side) pass and are all marked synthetic.
- The fixtures are current with their builder, every agent id they use exists in the catalog, and the harness adapters are current with the committed tests/agentic-board-suite/_build_harnesses.py (checked with `--check`). The adapters previously came from an uncommitted scratch script and could drift.
- The protocol references document exactly the rule table, no more and no fewer ids.
- subject_risk_tier and data_classification reuse the audit-event vocabularies, the board's actions are a subset of the schema's, and designated challengers exist in the catalog.
- The board agents are generic, static-review and experimental, bundle the protocol, and carry the tool-restriction declarations in five harness adapters; the board skills declare Read Grep Glob and link each reference.
- An AST denylist scan finds none of the listed wall-clock, network or randomness imports and calls in the rules or the fixture builder.
- The mutation-intent and instruction-bait patterns (LIVE_GUARD_INTENT and INSTRUCTION_BAIT) behave as pinned: the suite pins known misses, known false stops and bait negatives.
- Thirty-three targeted mutants (TargetedMutantTests) are each killed by the corpus.

### Rules added after the independent review

These rules were added, and the existing rules named in the last two bullets were changed, after the first review. The counts above include them. The rules added or changed after the second review are listed at the end of this section.

- DR-CHALLENGE-COMPLETE: every challenge on the proposer's envelopes sent no later than the request (or a decision-record binding it) is attached, so a HARD gate cannot be dropped by omission or by arriving late.
- DR-ONE-REQUEST: one decision-request is in force; re-asking supersedes an earlier one via supersedes_task_id.
- DR-OWNER-FROM-ROOT: a correlation carrying a decision-request is opened by a principal whose root names a decision_owner other than itself, and every decision-request goes to that owner, so the proposer cannot pick its decider.
- DR-CLASS-FROM-ROOT: decision_class is declared at the root, so a proposer cannot relabel an investment.
- DRC-ONE-RECORD, DRC-DECIDER-IS-ADDRESSEE, DRC-AFTER-REQUEST and DRC-COMPLETED: one decider's record per request, decided by the addressee, not before the request, with status completed.
- DRC-CO-SIGNED and DRC-CO-SIGN-BINDING: R5 dual control is two principal-sourced records (the decider's and the second approver's co-signing record on the same request, digest and outcome), not one record naming a second person. DRC-NOT-REQUESTER also covers the second approver.
- STOP-TERMINAL: a stopped message's only permitted child is an escalate, and no decision binds a stopped request.
- CH-ROUND-COUNTED: challenge rounds are counted per challenger, not self-declared, and a round-2 re-challenge is not a routing loop.
- HO-DESTINATION-TIER: every agent destination is a catalog agent with execution_tier static-review or read-only-runtime, which closes delegates to mutating live guards, untiered agents and non-catalog agents.
- HO-MONO-SPENT, HO-BLOCK-AS-CHALLENGE, HO-RETURN-EVIDENCE and VC-COST-SIGN are also new; their rows are in the protocol reference tables. VC-COUNTERFACTUALS now also requires a deterministic-workflow counterfactual.
- HO-SCHEMA now reads patterns as ECMA-262 (a trailing newline no longer passes an identifier) and reports malformed JSON, duplicate keys, non-object input and lone surrogates as HO-SCHEMA instead of a traceback.

After the first review, seven existing rule descriptions changed (DR-HARD-GATE, DR-NO-APPROVE-OVER-DISSENT, DR-UNRESOLVED-DISSENT, DRC-HARD-GATE-ACCEPTANCE, DRC-NOT-REQUESTER, DRC-SECOND-APPROVER, VC-COUNTERFACTUALS). Four of them gained the rule that the same challenger's later withdrawal (a HARD gate only by a HARD-gate withdrawal) clears a challenge.

Added or changed after the second review. DR-CHALLENGE-PRECEDES and HO-RETURN-TO-SENDER are new, and the counts above include them. The other rules named here changed.

- DR-CHALLENGE-PRECEDES (new): no attached challenge was sent after the request or descends from it, so a withdrawal sent after the request or after the decision cannot clear a HARD gate retroactively.
- HO-RETURN-TO-SENDER (new): a return is addressed to its parent's sender, so a reviewer's block verdict cannot skip the delegating agent and miss the decision path.
- HO-ESCALATE-TO-PRINCIPAL (changed): also covers any envelope with status escalated, because that status means the work is handed to a principal.
- STOP-ROUTING-LOOP (changed): a routing loop is agent-sourced only, so a principal may re-delegate to an agent already in the chain, and the one revisit is allowed only while the challenger has answered fewer than 2 of the sender's proposal envelopes in that chain.
- STOP-TERMINAL (changed): no decision-record binds a decision-request that declares any stop reason.
- CH-ROUND-COUNTED (changed): a round is one proposal envelope answered, so several challenges on one envelope share a round, and a round-2 revisit delivered after another challenger challenged in between is accepted.
- DR-CHALLENGE-COMPLETE (changed): a superseded request is judged as of its own sending while the request in force is still judged up to its decision, so a late challenge can be cured by superseding the request.
- DR-ONE-REQUEST (changed): a superseding request must come from the same proposer_agent, a supersession cycle is rejected, and a same-second supersede is accepted.
- DR-UNRESOLVED-DISSENT (changed): order is causal, so the same challenger's later withdrawal counts only when the challenge is its ancestor or was sent in an earlier second, and an unordered same-second withdrawal does not count.
- DR-NO-APPROVE-OVER-DISSENT (changed): the same causal order decides whether a challenge is still live, so an unordered same-second withdrawal does not lift the bar on recommending approval.
- DR-HARD-GATE (changed): a HARD gate clears only on a completed withdrawal in a strictly later counted round, sent after the finding, so a round-3 withdrawal stopped as over the round cap clears nothing.
- DRC-SECOND-APPROVER (changed): also applies when the bound decision-request is R5, not only when the decision-record's own tier is R5.
- DRC-CO-SIGNED (changed): a superseded request's record is void and owes no co-signature, while the decision in force still needs its co-signature.

### What it does not prove

- That any content is true, that any principal is who the record says, or that anyone approved anything.
- That any harness enforces its declared restriction, or that an agent follows its prompt. No model is run, so no routing or review quality is measured.
- That the rules and the fixture builder are free of ambient state. The scan is a denylist of specific imports and of calls written as a plain name followed by an attribute, so indirect forms pass it: `import datetime` with `datetime.datetime.now()`, `from time import time` with `time()`, and `os.urandom` were each replayed against the scan's logic on 2026-10-30 and none is caught. Determinism rests on code review as well as on the scan.
- That the mutation-intent and bait patterns are complete. LIVE_GUARD_INTENT and INSTRUCTION_BAIT are low-recall denylist canaries that fail open, and they are not runtime enforcement. An earlier version of this record called them broad and fail-closed and said bait negatives were pinned; both claims were wrong. A hostile objective can avoid them, and the agents are told to stop on meaning, not on the canary.
- That budgets hold across siblings. The gate checks budgets per chain (parent to child) only, and sibling fan-out is not bounded by the gate (open item RB-18).
- That a value case is real. The arithmetic and ordering rules check bookkeeping. Repository fixtures are synthetic and can never claim more than pilot status.
- Anything about product B behavior.
