## 2. What already existed, and what that changed

The brief assumed one Cilium agent, one skill and one live guard. The repository had more Cilium-adjacent ownership than that, and three findings reshaped the design before any agent was proposed.

**Finding R1 — CNI modernization is already owned.** `kubernetes-network-architecture-review-agent` covers CNI choice, overlay versus native routing, kube-proxy replacement, IPAM, MTU, dual-stack, Gateway API, ClusterMesh topology and egress architecture, and it explicitly hands policy content to the Cilium policy agent. A Cilium "network architecture" agent (brief §8.2) would be a second verdict on the same decision. Rejected; the transition-safety half moved to the lifecycle specialist.

**Finding R2 — BGP is unowned and unguarded.** No agent reviews Cilium BGP Control Plane resources, and neither `kubernetes-live-network-policy-guard-agent` (guards CNP, CCNP, NetworkPolicy, CiliumEgressGatewayPolicy) nor `kubernetes-live-network-architecture-mutation-guard-agent` (Service traffic policy, CoreDNS, Gateway API, ClusterMesh peer Secret; hard-refuses CNI replacement, kube-proxy swap, MTU, CIDR) covers BGP, LB-IPAM, L2 announcements or Helm upgrades. This is the largest gap, and it also bounds what the board may propose: those changes go to the human change process.

**Finding R3 — the Kubernetes maestro routing was incomplete.** Its prose routing table sent all Cilium requests to the policy agent, and its routing fixture has no Cilium domain at all; a request phrased only as "network policy" matches the architecture agent through the keyword `network`, and that agent refuses policy content. The prose table is fixed in this change. The fixture is generated by `tests/_generate_maestro_routing_fixtures.py`, which mines only the Kubernetes provider's own agents, so a hand edit would be overwritten; the fixture gap is recorded as residual risk in [06](./06-red-team-and-release-readiness.md).

Other existing capability reused rather than duplicated:

| Capability | Existing owner | Board use |
| --- | --- | --- |
| Board messaging envelope | `agentic-board-protocol` (`schemas/agentic-handoff.schema.json`) | Reused; no new schema |
| Verdict vocabulary | `docs/evidence-output-spec.md` (`approved`, `blocked`, `needs-review`; `verified`, `partial`, `assumed`) | Reused unchanged |
| Source registry | `references/evidence-ledger.md` + `tests/validate-skill-references.py` | Adopted for every Cilium skill; allowlist extended to Cilium-owned hosts |
| Harness rendering | `tests/agentic-board-suite/_build_harnesses.py` `render()` | Imported, not copied |
| Routing grader | `tests/validate-maestro-routing.py` `evaluate()` | Fixture expected files generated from it |
| Ticket and page authoring | `jira-ticket-authoring`, `confluence-document-authoring`, `atlassian-live-write-guard-agent` (ADR-0005) | Handoff contract only |
| Runtime detection rules | `falco-runtime-threat-rules-review-agent` | Tetragon deferred instead of duplicated |
| Cost judgment | `finops-maestro-agent` | Receives measurements from dataplane |
| Istio | the Istio board, `istio-maestro-agent` | Out of board |

The Istio board (a static maestro, six static-review specialists, a hand-maintained routing fixture, live changes handed to Kubernetes guards) is the repository-native shape, and the Cilium board follows it. One deliberate difference: the maestro skill is named `cilium-review-routing`, like `istio-review-routing`, not `cilium-maestro`, because the fixture generator discovers any `skills/<p>/<p>-maestro/` directory and would overwrite the hand-curated adversarial fixtures.

## 3. Capability matrix

Version applicability is Cilium 1.20.5 unless stated. "Owner" is the board member that holds the canonical reference; the evidence for each row is in that skill's `references/evidence-ledger.md`.

| Capability | Maturity (as documented) | Key prerequisites and limits | Failure mode that matters | Owner |
| --- | --- | --- | --- | --- |
| NetworkPolicy, CNP, CCNP | stable | 1.20 removes Kafka-aware and `l7proto` rules; 1.19 makes policies select local-cluster endpoints by default in a mesh | Removing default-deny; unrestricted egress to the metadata endpoint | policy |
| WireGuard encryption | stable; node-to-node encryption beta | Same-node traffic never encrypted; some N/S load-balancer and egress-gateway paths not encrypted with XDP or DSR | "Enabled" read as "covered" | policy |
| IPsec encryption | stable | Manual key rotation through a Secret | Rotation during upgrade | policy |
| Datapath maps (CT, NAT, policy, LB) | stable | Fixed caps; dynamic sizing from memory share; NAT at most 2/3 of CT | `CT: Map insertion failed` presents as intermittent timeouts | dataplane |
| kube-proxy replacement, socket LB, Maglev, DSR | stable | DSR dispatch limits by routing mode; toggling KPR live breaks existing connections | VIP unreachable with healthy pods | dataplane |
| Tunnel and native routing, MTU | stable | Overhead per encapsulation and encryption layer | PMTU black hole on large payloads | dataplane |
| Hubble and Relay | stable | Per-node ring buffer, default 4095 flows; three lost-event points | Absence of flow read as absence of traffic | evidence-boundary |
| BGP Control Plane v2 | stable | v1 `CiliumBGPPeeringPolicy` removed in 1.19; does not program the datapath | Session up, route not advertised or withdrawn under `externalTrafficPolicy: Local` | external |
| LB-IPAM | stable | Overlapping pools: later pool marked Conflicting | Allocation stops silently from one pool | external |
| L2 announcements | beta | Requires KPR; incompatible with `externalTrafficPolicy: Local`; failover 10-20 s by default | Clients that ignore gratuitous ARP | external |
| Egress gateway | stable | Requires BPF masquerade and KPR; incompatible with ClusterMesh, kvstore identity mode, CiliumEndpointSlice; no documented automatic failover | Gateway change breaks existing connections | external |
| ClusterMesh | stable | Unique name and ID, non-overlapping PodCIDRs, at most one minor version skew, `maxConnectedClusters` set once | Stale remote backends kept when a cluster is unreachable (`cacheTTL` default 0s) | external |
| Upgrades and rollback | — | One minor at a time, latest patch first; preflight is required and creates resources | Skipped minor; rollback after new features are consumed | lifecycle |
| CNI migration to Cilium | documented procedure | Dual overlay; policy enforcement off during migration; BGP routing and IP-family changes untested | Security exposure window during migration | lifecycle |
| Gateway API | Core conformance per Cilium docs | Requires KPR and L7 proxy; 1.20 requires Gateway API 1.6.1 or newer | TLSRoute objects disappear on the wrong CRD channel | lifecycle (upgrade note); design: Kubernetes architecture agent |
| Tetragon | separate project | Own tracing policies and enforcement | — | none (deferred) |

## 4. Enterprise pain register

Evidence labels: **D** documented upstream behavior (ledger-backed), **R** repository evidence, **H** hypothesis about enterprise practice that this design has not measured. No row is a measured enterprise observation; the frequencies are judgment.

| # | Pain | Root cause (mechanism) | Label | Consequence | Board owner |
| --- | --- | --- | --- | --- | --- |
| P1 | Intermittent timeouts while Kubernetes reports healthy | Datapath state (CT, NAT, LB maps) exhausted or stale while API objects are correct | D | Long incidents, "it's the network" escalations | dataplane |
| P2 | Default-deny rollout breaks a dependency | Dependency inventory built from incomplete telemetry; DNS egress forgotten | D + H | Production outage | policy |
| P3 | Uncontrolled egress, metadata endpoint reachable | Broad `toCIDRSet` without exceptions | D | Credential exposure | policy |
| P4 | "Encrypted in transit" claim not true for every path | Documented coverage gaps (same-node, XDP, DSR, initial packets) | D | Failed control assessment | policy |
| P5 | Upgrade breaks a fleet | Skipped minor, removed CRD kinds, kernel below minimum on one pool | D | Wide outage, no clean rollback | lifecycle |
| P6 | Advisory triage by headline | Applicability needs version AND enabled feature | D | Wasted emergency patching, or missed exposure | lifecycle |
| P7 | LoadBalancer IP unreachable from the datacenter | Advertisement withdrawn by traffic policy, or peer-side filtering invisible to the cluster | D + H | Regional unavailability | external |
| P8 | Third-party allowlist breaks after a node change | Egress gateway selection by lexical order; gateway change breaks connections | D | Partner integration outage | external |
| P9 | DR plan assumes ClusterMesh failover | Stale endpoints retained; connectivity is not application DR | D | False business-continuity confidence | external |
| P10 | Incident evidence cannot support the conclusion | Bounded Hubble buffers, lost events, unmanaged pods | D | Wrong root cause, false closure | evidence-boundary |
| P11 | Diagnostic bundles leak secrets | Sysdump and bugtool collect configuration and, historically, a WireGuard key | D | Credential exposure in tickets | evidence-boundary |
| P12 | Nobody knows who owns a Cilium symptom | Several plausible owners per symptom | R + H | Slow triage | maestro |
| P13 | Fleet configuration drift | Hundreds of clusters diverge | H | Unpredictable behavior | not an agent: deterministic diff (deferred) |
| P14 | Process-to-network correlation for intrusions | Needs Tetragon or Falco evidence | H | Slow incident response | deferred runtime-security board |

## 5. Unresolved questions

- Q1: How often do real users bring Cilium requests that span domains? This decides whether the maestro earns its hop ([02 §5](./02-opportunity-scoring.md)).
- Q2: Do users typically have peer-router evidence? If not, the external specialist will mostly return `needs-review` on BGP.
- Q3: Which managed Cilium distributions do users run? Upstream notes are necessary but not sufficient for them.
