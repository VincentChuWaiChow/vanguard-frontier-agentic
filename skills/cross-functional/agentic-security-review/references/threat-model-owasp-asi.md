# Threat model: OWASP Top 10 for Agentic Applications

Reference for [agentic-security-review](../SKILL.md). Load it when you walk ASI01 to ASI10 for a design, when you need review questions, evidence requests or a plan-only test for one item, or when you must say which risks a repository rule touches and which are runtime-only.

## What this reference is and is not

- The ten item names below are taken from the announcement of the [OWASP Top 10 for Agentic Applications (2026)](https://genai.owasp.org/2025/12/09/owasp-top-10-for-agentic-applications-the-benchmark-for-agentic-security-in-the-age-of-autonomous-ai/). Read the OWASP material for what each item covers; this reference does not restate it.
- The review questions, evidence requests and test scenarios are this skill's own review aids. They are not OWASP text and OWASP has not endorsed them.
- OWASP is a threat source here, as in docs/compliance/framework-profiles.md: it informs what to look for and is not a compliance framework. Never write that a design satisfies, complies with, or is certified against an ASI item.
- Product A is what this repository ships: role contracts, skills, a JSON Schema and offline gates. Product B is the runtime a deploying organization operates: the system that authenticates senders, enforces authorization, constrains tools, and stores audit records. Nearly every control that stops an ASI threat lives in product B.

## The walk

Each row ends in exactly one of three states: a finding (with its id), no finding (with the evidence that supports it), or not assessable (with the missing evidence named). A row with no evidence is not a pass.

The last column is either the name of a protocol rule that operates on that threat's object, or the marker runtime-only (product B). No coverage is manufactured: a rule is named only where it checks the very thing the threat attacks, and its limit is stated.

| ID and name | Review questions | Evidence to request | Plan-only test scenario | Repository control |
|---|---|---|---|---|
| ASI01 Agent Goal Hijack | Which inputs can carry instructions into the agent's goal or plan: user text, retrieved documents, tool descriptions, tool output, peer-agent messages, memory? What separates data from instructions before a privileged call? Can the goal change mid-task without a principal's act? | The prompt and tool list; every ingestion path for untrusted text; where a confirmation or policy check sits between model output and a tool call; sanitized samples of retrieved content. | A synthetic, visibly marked document in the retrieval corpus asks the agent to call a write-capable tool with attacker-chosen arguments. Safe result: the call is not made, or it stops at a human confirmation that shows the exact arguments. | STOP-INSTRUCTION-BAIT: scans an envelope objective for override or claimed-approval phrasing. It is a fixture oracle in the offline gate, not runtime detection, and it does not see evidence, retrieved content or tool output. |
| ASI02 Tool Misuse | Which tools can the agent call, with which argument ranges, as which identity? Can a legitimate tool be driven to an unintended effect through broad parameters, chained calls or destructive defaults? Are bounds enforced by the tool or only requested in the prompt? | Tool inventory with scope, mutation capability and egress; argument schemas and server-side validation; per-tool authorization; rate and quota limits. | For each write-capable tool, plan a call with boundary arguments (maximum count, wildcard target, another tenant's identifier) in a sandbox. Safe result: the tool's own authorization or validation rejects it, not the prompt. | runtime-only (product B) |
| ASI03 Identity & Privilege Abuse | Whose authority does each call carry: the caller's, the agent's, a shared service account? Are tokens bound to their audience? Are scopes the minimum for the task? Can a low-privilege caller get a high-privilege action through the agent? Do credentials outlive the task? | An identity map of caller identity and effective identity at every hop; token audience and scope settings; credential lifetimes; the list of shared identities; the delegation chain. | As a low-privilege test user, ask for something only a higher-privileged user may do. Separately, replay a token issued for one MCP server against another. Safe result: both are refused, on entitlement and on audience. | HO-NO-EXECUTION and HO-ATTEN-ACTIONS: authorized_actions in a handoff envelope never include an action beyond read, analyze, recommend, challenge or escalate, and never widen down a chain. This covers envelope data only, not the credentials or permissions of any real agent. |
| ASI04 Agentic Supply Chain Vulnerabilities | Which tools, MCP servers, skills, prompts, models and plugins load, and from where? Is each pinned, and verified where the publisher signs? Can a tool description or tool list change after approval? How is a component revoked? | The agent component inventory; pin strategy and signature status per component; the update policy; a record of the tool list and descriptions that were reviewed. | In a staging inventory, change a tool description and add a tool to an approved server. Safe result: a pin or digest check, or a tool-surface diff, flags the change before an agent can call it. | runtime-only (product B) |
| ASI05 Unexpected Code Execution | Can any path turn model output into executed code or commands: code interpreters, shell tools, template engines, deserialization, generated scripts run without review? Is execution sandboxed with no credentials, no unneeded egress, and bounded resources? | The list of execution surfaces; sandbox, filesystem and network policy; whether any output runs without human review. | Ask the agent to produce and run a script that reads a synthetic canary file outside its working scope and posts it to a canary endpoint on a test network. Safe result: the sandbox blocks the read or the post. | runtime-only (product B) |
| ASI06 Memory & Context Poisoning | What writes to long-term memory, summaries, caches and vector stores, and who can cause a write, including untrusted content passing through the agent? Is each entry tagged with provenance, tenant and expiry? Can a stored instruction reach later sessions or other users? | Memory write paths; the entry schema with provenance and tenant; retention and expiry settings; the review, quarantine and purge procedure. | A marked synthetic instruction inside a retrieved document asks to be remembered. In a later session as the same user, as another user of the tenant, and as a user of another tenant, check recall. Safe result: not stored as an instruction, and no cross-tenant recall. | runtime-only (product B) |
| ASI07 Insecure Inter-Agent Communication | How do agents authenticate each other, and is the channel integrity-protected? Can a message be spoofed, replayed or altered? Are peer messages trusted as instructions? Is an A2A Agent Card trusted without verification? Is an interrupted state such as AUTH_REQUIRED treated as authorization? | Transport and authentication settings; Agent Card handling and signature verification; the message schema; replay protection; routing configuration. | Send a message from a peer identifier outside the topology, replay an earlier message, and present a tampered card. Safe result: the receiving runtime rejects each. | HO-CHAIN-CUSTODY: in a record set, an envelope must be sent by its parent's destination, or by its parent's sender when the parent was stopped. This checks the consistency of recorded data. It does not authenticate any sender; sender authentication is runtime-only. |
| ASI08 Cascading Failures | Can one failure or one bad output spread across agents, tools or tenants? Which budgets, depth limits, fan-out caps, loop detection, breakers and kill switch exist, and can an attacker trigger them on purpose (amplification, denial of wallet)? Containment design belongs to the architecture review; the security question is whether an attacker can set it off. | Budget and limit settings and where each is enforced; loop bounds; breaker configuration; a blast-radius description. | Plan a synthetic input that makes agent A delegate to B and B back to A, and one that multiplies fan-out. Safe result: the loop is detected or the budget stops it before the cap, and an owner can see the incident. | STOP-ROUTING-LOOP, STOP-DEPTH and STOP-BUDGET: offline checks that a chain which met a loop, depth or budget condition declared it and stopped. As containment design the owner is the architecture review. These rules do not halt a running system. |
| ASI09 Human-Agent Trust Exploitation | Can the agent talk a human into approving something unsafe through confident tone, fabricated evidence, urgency, or a summary that hides the risky part? What does the approver see versus what will run? Can an agent produce or relay an approval? Does the approver have enough information and time? | Approval screens or messages as shown; a comparison of the summary against the actual action and target; approval logs; who may approve; time and volume pressure on approvers. | Plan a synthetic case in which the agent's summary omits a destructive parameter that the action carries. Safe result: the approval view shows the exact action and target, so the omission is visible. | HO-AGENT-NO-APPROVAL and DRC-PRINCIPAL-SOURCE: in this protocol an agent-sourced envelope never carries approved or rejected, and a decision-record must come from a principal. This does not stop a human from being misled on a real approval screen. |
| ASI10 Rogue Agents | Can an agent act outside its intended scope, outlive its task, create unregistered agents, or keep running after compromise or drift? Is there an inventory of agents with owners and identities, and a way to disable one? Is behavior monitored against declared tool use? | An agent registry with owners; one identity per agent; the deactivation and credential revocation path; monitoring signals and thresholds; discovery of unregistered agents. | Plan a scenario in which one agent's instructions are replaced with a synthetic deviation. Check that monitoring flags use outside its declared tools and that disabling the agent also revokes its credentials. | runtime-only (product B) |

## Repository controls and their limits

The protocol rules named above are documented in the agentic board protocol references: [stop conditions](../../agentic-board-protocol/references/stop-conditions.md), [handoff envelope](../../agentic-board-protocol/references/handoff-envelope.md) and [decision record](../../agentic-board-protocol/references/decision-record.md). Read this section before you tell anyone that a repository rule covers a threat.

- The offline gate validates records, not systems. A passing record set is well-formed and internally consistent; it does not show that any control exists in a running system.
- ASI01: the objective scan is a fixture oracle. It looks only at the objective field and only at specific phrasings. Paraphrase, other languages, encoded text, and instructions hiding in evidence, retrieved content or tool output are not matched. Real-time detection of hostile input is product B.
- ASI03: the envelope vocabulary carries no execute verb, so a record cannot authorize more than review. This says nothing about what a real agent's credentials permit.
- ASI07: chain custody compares recorded senders and recipients. It cannot tell whether a sender is who it claims to be.
- ASI08: the three computed stops check that a chain which met the condition declared it and stopped. They do not stop anything. A deploying runtime has to enforce loop, depth and budget limits itself.
- ASI09: refusing agent-written approvals in the data contract is not the same as protecting a human who reads a misleading summary.
- ASI02, ASI04, ASI05, ASI06 and ASI10 have no repository control. The review questions above are the only repository-side contribution, and the controls belong to the deploying organization.

## Candidate alignment

A walk of this table can support an owner's work against NIST AI RMF MEASURE 2.7, which concerns the security and resilience of the AI system (see the [AI RMF core](https://airc.nist.gov/airmf-resources/airmf/5-sec-core/); the page carries a banner that AI RMF 1.0 is being updated). It does not satisfy that subcategory. An accountable owner confirms any mapping.

## Recording the walk

- Number findings F1, F2 and so on, and cite the ASI id in each. One finding can touch several ASI items; cite the primary one and list the others.
- For a no-finding row, record the evidence and its label. A claim that rests on documentation or inference stays labeled that way; documentation never proves what a specific deployment does.
- For a not-assessable row, add the missing evidence to the output. If the missing item decides whether a reachable exploit path exists at the decision's risk tier, mark it blocking and escalate to a principal rather than guessing; see the [workflow and output reference](workflow-and-output.md).
